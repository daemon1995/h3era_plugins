# ERA Runtime Services

Общие сервисы времени выполнения для плагинов ERA и ERM: графические ресурсы, текстовые привязки, экспорт конфигурации, владение объектами, мини-карта, подсветка, replay и замена объектов по геометрии.

Название проекта — **ERA Runtime Services**, каталог — `ERA_RuntimeServices`, файл проекта — `ERA_RuntimeServices.vcxproj`, бинарник — `ERA_RuntimeServices.era`, версия `1.0.0-rc1`. Исправления и порядок проверки: [RELEASE_CHECKS.md](Docs/RELEASE_CHECKS.md). Первоначальная оценка: [RELEASE_REVIEW.md](Docs/RELEASE_REVIEW.md).

Плагин `ERA_RuntimeServices.era` добавлен в `H3EraPlugins.sln` (Debug/Release, x86). Он направляет зарегистрированные объекты в штатную отрисовку DEF с цветом владельца. Подходящие пиксели флага должны уже присутствовать в DEF; плагин не добавляет отдельную картинку флага. Изменение игровых наград, посещение и захват остаются задачей скрипта.

При отрисовке ERM не вызывается: два горячих хука option 879 заменены C++ LoHook. Получение владельца кэшируется в памяти. Нативная отрисовка сохраняет анимацию, границы экрана и порядок слоёв. Мини-карта получает цвет объекта внутри штатной проверки видимости, после проверки маркера героя.

Для HD_WOG добавлены отдельные хуки его 16/32-битного рисования: плагин передаёт цвет в штатную ветку HD-маркеров, сохраняя изменяемый размер мини-карты и окраску при уменьшении больших карт. Точки находятся по сигнатурам загруженной DLL; файл HD-мода не изменяется. Адреса, способ подключения и проверки описаны в [HD_MINIMAP.md](Docs/HD_MINIMAP.md).

Отрисовка вынесена в `ObjectRendering.cpp`/`ObjectRendering.h`. Мини-карта окрашивает занятые клетки и вход реального объекта, сохраняя штатное масштабирование HD; фон и проходимая часть DEF не увеличивают маркер. Установка и причины отказа HD-хуков диагностируются один раз для загруженного модуля.

## API

`ConfigExport` принимает типизированные поля и владеет JSON-снимками, фильтрами, счётчиками и сериализацией. JSON-библиотека находится только в общей реализации API; провайдеры и LocaleManager используют лёгкие клиенты. Используется один типизированный контракт без переходников JSON-строк.

Конфигурация, текстовые привязки, общий каталог объектов и расширяемый экспорт: [CONFIG_SERVICES.md](Docs/CONFIG_SERVICES.md). Таблицы сервисов публикуются в памяти патчера, RMG сохраняет материнский API экстендеров, LocaleManager использует общий UI экспорта.

Общий графический сервис для кадров артефактов и портретов жилищ: [GRAPHICS.md](Docs/GRAPHICS.md). Он предоставляет версионированный C ABI, владеет кадрами/ресурсами, кэшем и палитровыми render hooks; оба расширителя используют один экземпляр сервиса.

Добавлен API замены объектов по действующим маскам и координатам входа. Контракт, JSON-правила, ограничения v1 и проверки описаны в [OBJECT_REPLACEMENT.md](Docs/OBJECT_REPLACEMENT.md).

Все экспорты имеют недекорированные имена и соглашение `__stdcall`. Заголовок для C++: `headers/EraPluginsAPI/ErmFunctionsAPI.h`. Через ERM вызываются `SN:F^ERA_RuntimeServices:ИмяФункции^/...`; результат находится в `v1`. Такой синтаксис требует ERA 3.9.29 или новее. В более ранних версиях DLL можно вызывать через адрес экспортированной функции и `SN:E`.

| Экспорт | Аргументы | Результат |
|---|---|---|
| `Erm_RegisterObjectType` | `type, subtype, drawOnMinimap` | `1` — зарегистрирован, `0` — ошибка |
| `Erm_SetObjectOwner` | `x, y, z, owner` | `1` — назначен (включая прежнего владельца), `0` — ошибка |
| `Erm_GetObjectOwner` | `x, y, z` | `-1` — нейтральный, `0..7` — игрок, `-2` — ошибка |
| `Erm_RegisterReplayEvent` | `redoFunction, undoFunction, x1, x2, x3, x4` | `1` — событие записано, `0` — ошибка |
| `Erm_RegisterReplayEventArgs` | `redoFunction, undoFunction, int* args, argCount` | `1` — событие записано, `0` — ошибка |
| `Erm_ReadJsonInt` | `const char* key, defaultValue` | целое из JSON либо переданное значение по умолчанию |
| `Erm_ReadJsonIntArray` | `const char* key, int* output, capacity` | размер при `output=0/capacity=0`; иначе число записанных целых |

JSON-читатели используют текущие данные языка ERA без собственного кэша. Числа проверяются как знаковые 32-битные целые; пустые, дробные, переполненные и некорректные значения отклоняются. Массив читается из последовательных ключей `key.0`, `key.1`, ... до первого отсутствующего индекса; скаляр тоже поддерживается. Некорректный элемент возвращает `0` без записи части массива. Запрос размера не собирает временный массив; при заполнении буфера временно хранятся только помещающиеся в него числа, но проверяется вся последовательность. Строка индексированного ключа используется повторно. Переданный буфер принадлежит вызывающему коду и должен вмещать `capacity` целых; функция записывает не более этого количества.

В `wogify_merged` общий `WOG_IFY_ReadIds` определяет размер, выделяет ERM-массив и заполняет его вторым вызовом API. Это убирает отдельные ERM-вызовы чтения, преобразования и добавления каждого ID. `WOG_IFY_ReadInt` использует нативный числовой читатель. Адреса обновляются после загрузки карты и перед вогификацией; при отсутствии новых экспортов сохраняется прежний ERM-путь. Изменения времени выполнения в игре пока не измерены. Проверки обоих читателей включены в `run-tests.cmd`. Горячий путь замены теперь напрямую вызывает удаление WoG из EXE, использует геометрию без копирования векторов и локальный буфер выбора прототипа. Замеры отдельных операций и их ограничения приведены в `OBJECT_REPLACEMENT.md`.

Координаты обозначают вход объекта (жёлтую клетку), а не нижний правый угол DEF. Поддерживается объект под стоящим на входе героем. Недопустимые координаты, отсутствующий подземный уровень и незарегистрированные объекты отклоняются. Допустимые владельцы: `-1..7`.

Типы: `0..231`; подтипы: `0..32767`, либо `-1` для всех подтипов. Точная регистрация имеет приоритет над `-1`. Повторная регистрация обновляет настройку мини-карты; флаг `drawOnMinimap` принимает только `0` или `1`. На мини-карте используются штатные цвета владельцев, включая нейтральный цвет для `-1`. Отрисовка флага действует для объёмных объектов, проходящих штатную ветку отрисовки; плоские объекты сохраняют поведение игры.

Регистрация нужна при каждом входе на новую/загруженную карту, например в `!?FU(OnGameEnter)` или при создании ERM-хуков опции. Для option 879 регистрируются водяная мельница, ветряная мельница, мистический сад и склад (`142`). Автоматической регистрации нет: плагин работает только с запрошенными скриптом типами.

```erm
!!SN:F^ERA_RuntimeServices:Erm_RegisterObjectType^/(OBJ_WINDMILL)/-1/1;
!!SN:F^ERA_RuntimeServices:Erm_SetObjectOwner^/(x)/(y)/(z)/(owner);
!!VR(success:y):Sv1;
!!SN:F^ERA_RuntimeServices:Erm_GetObjectOwner^/(x)/(y)/(z);
!!VR(owner:y):Sv1;
```

## Подсветка непосещённых объектов

Редкие поднимающиеся искры рисуются перед туманом войны (`0x412180`). Последовательность из 128 кадров с шагом 128 мс перенесена из предоставленного HotAPatcher 1.03. Два потока с разными фазами и горизонтальными позициями дают вдвое большую плотность при прежней скорости движения. DEF задаёт горизонтальные границы, нижнюю точку эффекта и оттенок искр: палитра строится по среднему цвету непрозрачных пикселей текущего кадра, без теней. Цвет не зависит от награды. Сплошной заливки и контура нет. Состояние посещения и награда читаются на входе существующими методами API/H3API, включая объект под героем. Видимость проверяется для каждого отрисовываемого тайла: знание входа и остальных частей объекта не требуется, неизвестные клетки не подсвечиваются. Маска текущего кадра строится штатным декодером на двух фонах и кэшируется до смены карты; полупрозрачные тени не влияют на границы. Порядок слоёв учитывает перекрывающие объекты. Размер поверхности, шаг строки и режим 16/32 бит берутся из игры. Как в HotAPatcher, пиксели искр используют цвет палитры без аддитивной заливки. Игровой генератор случайных чисел не затрагивается.

По умолчанию поддерживаются мельницы, водяные колёса, мистические сады, навесы (39), банки существ (включая утопии, склепы и корабли), пирамиды, святилища, деревья знаний, университеты, повозки, могилы воинов, хижины ведьм, фонтаны удачи, обелиски и палатки ключника. Для наград проверяется наличие содержимого, для посещений — игрок; посещения отдельными героями сюда не относятся. Склад ERA (142) автоматически распознаётся, если скрипт зарегистрировал его через `Erm_RegisterObjectType`; также его можно явно включить через `Erm_SetObjectGlow`. В SoD тип 142 обозначает декорацию, поэтому без регистрации он не подсвечивается.

Все методы — `__stdcall`, экспортируются без декорации:

```cpp
int Erm_SetObjectGlow(int type, int subtype, int enabled);
int Erm_SetObjectGlowEnabled(int enabled);
int Erm_GetObjectGlowEnabled();
```

Первые два возвращают `1` при успехе, `0` при неверных параметрах. `enabled` — `0/1`; тип — `0..231`; подтип — `0..32767` или `-1` для всех. Точная настройка имеет приоритет над общей. `Erm_SetObjectGlow` добавляет либо отключает пару тип/подтип независимо от регистрации флагов. Для явно добавленных нестандартных типов подразумевается штатная маска посещения игроками в битах `5..12` поля setup; специальная раскладка склада 142 поддержана отдельно.

```erm
!!SN:F^ERA_RuntimeServices:Erm_SetObjectGlow^/(OBJ_WINDMILL)/-1/0;
!!SN:F^ERA_RuntimeServices:Erm_SetObjectGlow^/(OBJ_WINDMILL)/0/1;
!!SN:F^ERA_RuntimeServices:Erm_SetObjectGlowEnabled^/1;
```

Переопределения типов очищаются при выходе/загрузке карты, как регистрации флагов; скрипт повторяет их при входе на карту. Общий выключатель сохраняется в процессе. Сам Runtime Services не читает INI и не имеет пользовательских настроек. Внешний ERA_SystemOptionsExtension хранит `AdvMap.ObjectGlow` у себя и вызывает API плагина.

В RC маски хранятся битами с пределом 16 МиБ полезных данных и 4096 кадров; поверхности декодирования переиспользуются. Состояние посещения читается один раз на часть объекта, нижние перекрывающие объекты до первой искры не декодируются, на экран выводятся только активные пиксели искр. Внешний вид сохранён. Профилирование управляется только API: `Erm_SetObjectGlowProfiling(1)` начинает новый замер, `Erm_SetObjectGlowProfiling(0)` останавливает его, `Erm_GetObjectGlowProfile` копирует счётчики в структуру `erm_functions::ObjectGlowProfile`. Автоматического вывода статистики нет. Порядок сравнения приведён в [RELEASE_CHECKS.md](Docs/RELEASE_CHECKS.md).

## Файлы проекта и исключения

`Source/Core` содержит инициализацию, владение и replay; `Source/Objects` — отрисовку, свечение и замены; `Source/Graphics` — кадры и палитры; `Source/Config` — общие конфигурационные и текстовые сервисы. Документация находится в `Docs`, проверки — в `Verification`, отключённый экспериментальный декодер — в `Research`. Фильтры Visual Studio повторяют структуру; внешние заголовки вынесены в `Shared`.

`noexcept` используется для небросающих операций и API с обработанными ошибками выделения памяти. Он не заменяет `try/catch`: необработанное исключение внутри `noexcept` приводит к `std::terminate`. Контейнеры и JSON выделяют память, поэтому их границы API сохраняют обработку ошибок. Хуки replay и замена объекта могут вызвать ERM/нативные обработчики и штатный выход из карты: они намеренно допускают раскрутку стека с RAII, включая `/EHa`. Проверки входных параметров, ресурсов и доступности карты сохраняются; обязательные глобальные объекты в штатной отрисовке повторно не проверяются.

## Сохранение и выход

Владелец хранится в `i^ERA_RuntimeServices.Owner.<packedCoords>^` через `Era::SetAssocVarIntValue(name, owner + 1)`. Упаковка: `(x & 1023) | ((y & 1023) << 16) | ((z & 1) << 26)`. Отсутствующая переменная/значение `0` означает владельца `-1`; игроки кодируются как `1..8`. Нейтральные объекты не создают переменных при чтении.

Переменная обновляется при смене владельца и сохраняется штатным механизмом ERM вместе с картой. Собственная savegame-секция не требуется. На `OnAfterLoadGame` кэш владельцев сбрасывается и далее читается из восстановленных переменных. На `OnGameLeave`, `OnGameLeft`, `OnBeforeLoadGame` очищаются регистрации, кэш и replay. Сами ERM-переменные загружаются/сбрасываются движком ERA. Менять их следует через API, чтобы кэш соответствовал сохранению. `PO:O` — отдельное хранилище и автоматически с API не синхронизируется.

Удаление через штатную WoG-точку `DelObject` (`UN:O` и API замены) очищает владельца после удаления экземпляра. При отклонённом удалении владелец сохраняется; во время replay меняется только временное представление. При стороннем удалении в обход этой точки вызывающий код должен нейтрализовать объект через API до его удаления.

## Replay хода

Изменение владельца через API записывается автоматически. При replay владельцы откатываются перед начальным кадром и затем меняются между соответствующими штатными действиями. Воспроизведение использует временные значения: ассоциативные переменные и итоговое владение не переписываются.

Для произвольного события вызовите `Erm_RegisterReplayEvent` после выполнения настоящего события. Регистрация только запоминает callback и копирует параметры; сразу callback не вызывается. `redoFunction` — числовой ID ERM-функции, `undoFunction` — ID функции отката либо `0`. Callback получает записанные параметры в `x1..x4`; остальные `x` обнулены. Вариант `Args` принимает до 16 целых значений и копирует их, поэтому исходный массив можно освобождать. Аргументы — целые значения, а не сохраняемые указатели на временные строки/объекты.

```erm
!!SN:F^ERA_RuntimeServices:Erm_RegisterReplayEvent^/(MyEventRedo)/(MyEventUndo)/(x)/(y)/(z)/(value);
```

Undo вызывается в обратном порядке, redo — в прямом, включая несколько событий между одними и теми же действиями. Для callback, меняющего игровой мир, откат реализует скрипт. Для уведомления/эффекта можно передать `undoFunction = 0`. Повторная регистрация событий во время replay отклоняется; вызов `Erm_SetObjectOwner` из callback меняет только временное владение. Буфер аргументов ERA восстанавливается после callback, в том числе при системном исключении выхода/загрузки (`/EHa`).

События очищаются вместе со штатным списком действий при начале нового периода записи, а также при выходе/загрузке. Они **не записываются в сейв и не передаются по сети**. После загрузки воспроизведение старого штатного журнала не содержит событий плагина. Кнопка replay и скорость просмотра остаются штатными; нужны действия в штатном журнале, чтобы игра разрешила просмотр. Прерывание анимации просмотра клавишей по-прежнему применяет все действия и callbacks.

## Перевод option 879

В `examples/option 879 - capture mills and gardens.erm` находится адаптированная копия приложенного скрипта: убраны ERM-хуки отрисовки и их обработчики, добавлена регистрация типов, все обращения к `PO:O` переведены на API. Остальные хуки опции, замены DEF, сетевой вызов функции захвата, награды и подсказки сохранены. Скопировать нужно **вместо** исходного скрипта, с тем же именем, а не загрузить оба одновременно.

Для старых сейвов есть однократный импорт владельцев из `PO:O` при первом входе с новой версией. Маркер `ERA_RuntimeServices.Migrated879` сохраняется в ERM. Значения `PO:V0/V1` остаются в исходном хранилище.

`ERA_RuntimeServices.era` и обновлённый option 879 устанавливаются вместе; комплект и порядок установки описаны в [RELEASE_CHECKS.md](Docs/RELEASE_CHECKS.md). Сохранения экспериментальных API-сборок не являются релизным форматом; импорт из выпущенного варианта option 879 через `PO:O` сохранён.

## Проверка

`run-tests.cmd` запускается из Developer Command Prompt Visual Studio. Проверяет точные/общие регистрации, границы параметров, порядок undo/redo, временное владение и выбор клеток мини-карты. Также проверяет геометрию замены, кэш и выделения памяти; отдельный `Verification/run-object-replacement-hooks-tests.cmd` проверяет ABI с настоящим patcher. Если передать путь к `HD_WOG.dll`, проверяются также сигнатуры на реальном файле, ASLR и отказ при изменённом контракте. `Verification/verify_hd_marker_path.py` проверяет исходные инструкции HD в эмуляторе (48 случаев). Бинарники тестов помещаются в игнорируемый `ERA_RuntimeServices/build`.

Сборка отдельного проекта:

```text
msbuild ERA_RuntimeServices\ERA_RuntimeServices.vcxproj /p:Configuration=Release /p:Platform=Win32
```

По общим настройкам репозитория такая сборка устанавливает файл в `Mods/WoG/eraplugins`. Для проверки без установки задайте абсолютные `PluginOutDir` и `IntDir` внутри отдельного рабочего каталога.

Исторически Debug и Release проверялись с локальным `v141_xp`. Результаты текущего RC и оставшиеся игровые проверки перечислены в [RELEASE_CHECKS.md](Docs/RELEASE_CHECKS.md).

Адреса сверены с локальным IDA-экспортом `h3era HD.exe`: `410B60` (флаг, `EDI=H3ObjectAttributes`, координаты `[EBP-44h]`), `412BA0` (мини-карта, `EBX=H3MapItem`, цвет `SI`), `4FF280` (вход DEF), `49D410` (undo/redo штатного журнала), `49D2A0` (очистка). Хуки: `410DCA`, `410F7C`, `412F33`, `49D4F8`, `49D50D`, `49D5A5`, `49D608`; HiHook: `49D410`, `49D2A0`. Начальные инструкции в 11 точках хуков/переходов дополнительно совпали с установленным `D:/games/HoMM 3 ERA/h3era HD.exe`. Требуется совместимая адресная база ERA/SoD. Визуальная проверка новой HD-совместимости в запущенной игре ещё нужна.

Игровые проверки: новый объект без владельца → захват двумя разными игроками → нейтрализация; подтипы с разными настройками мини-карты; объект под героем и закрытый туманом; сохранение/загрузка; выход и новая карта тех же координат; два просмотра одного хода; события до первого/после последнего штатного действия; выход/загрузка из callback; передача хода в сети. При обычной перерисовке ERM-log не должен получать вызовов функций отрисовки option 879.
