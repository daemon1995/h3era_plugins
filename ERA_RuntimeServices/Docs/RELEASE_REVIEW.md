# ERA Runtime Services — оценка перед релизом

**Исторический аудит до исправлений.** API и новые ERM-скрипты ещё не выпускались. Актуальные исправления и проверки описаны в [RELEASE_CHECKS.md](RELEASE_CHECKS.md). Замечания ниже фиксируют исходное состояние, а не текущий список незакрытых дефектов.

Дата: 24.10.2026. Проверен текущий рабочий каталог, включая незакоммиченные изменения. Исторические отчёты в документации рассмотрены как свидетельства прежних проверок, а не как результаты этого аудита. Игровые файлы не обновлялись.

## Вывод

Проект нужен: это уже используемый общий слой для нескольких плагинов и двух скриптовых подсистем. Техническая основа достаточно зрелая для подготовки release candidate. Для стабильного релиза всего комплекта пока недостаёт проверки актуальной сборки в игре и определённого поведения при частичном отказе замены объектов.

Не следует обещать, что все функции востребованы одинаково: графика и экспорт имеют несколько реальных клиентов; произвольные replay-callback пока представлены примером. Автоматический replay владения при этом используется кодом API.

## Название и границы

**ERA Runtime Services** отражает назначение: потребители — и C++-плагины, и ERM; функции не ограничиваются вызовами ERM. Единое техническое имя каталога, проекта и бинарника — `ERA_RuntimeServices`.

Клиенты и ERM-скрипты используют `ERA_RuntimeServices.era`; собственные ключи сохранений — `ERA_RuntimeServices.Owner.*` / `ERA_RuntimeServices.Migrated879`. Экспорты `Erm_*` и контракты `ERA.Services.*` сохраняют названия API. Совместимость с прежними внутренними именами не требуется.

Один бинарник сейчас оправдан общими потребителями и единым владением ресурсами. Внутреннее разделение по модулям полезнее немедленного дробления на несколько DLL. Подсветка — отдельная пользовательская возможность; её зависимость от общего сервиса не делает её обязательной частью поведения любого будущего клиента API.

RuntimeServices.h — механизм обнаружения, а не перенос всех владельцев внутрь ERA_RuntimeServices.

## Существенные замечания

1. **P1 — частичный отказ замены неотличим от отказа без изменения карты.** В ObjectReplacement.cpp:304 исходник удаляется, затем вызывается размещение, и последующие проверки могут вернуть 0. Восстановления исходного объекта нет. wogify_merged после результата, отличного от TRUE, продолжает цикл без инициализации награды. Предварительная загрузка DEF снижает риск, но не обеспечивает атомарность. До стабильного выпуска определить контракт: восстановление поддерживаемых объектов либо отдельный статус частичного изменения с явной обработкой вызывающим скриптом. Тестировать отказ после удаления на реальном конвейере.

2. **P1 для комплекта WoG Scripts — замены отключены в сети.** Обе операции Find/Replace немедленно возвращают 0 при H3Network::Multiplayer(). Защита от рассинхронизации оправданна, но перенесённые из старого конвейера правила в сетевой игре не выполняются. Это ограничение поведения, а не готовая поддержка сети. Для релиза комплекта нужны либо поддержанный сетевой путь, либо явно заявленная граница функциональности и проверенный сценарий вогификации без этих замен.

3. **P2 — готовность не соответствует успеху всех хуков.** ObjectRendering::InstallHooks и glow::InstallHooks не проверяют результат записи. OnAfterWog в dllmain.cpp:237 безусловно устанавливает hooksReady=true, также не проверив replay-хуки. При отказе установки регистрация может сообщать успех без нужной отрисовки/replay. Возвращать результаты по подсистемам, проверять связанные наборы хуков и писать одну содержательную диагностику при отказе. GraphicsResources и ObjectReplacement уже показывают подходящий локальный образец проверки.

4. **P2 — незаметное отключение HD-маркеров.** EnsureHdMinimapHooks безопасно отвергает неизвестную/конфликтующую HD-разметку, но не сообщает причину. checkedHdModule записывается до установки, поэтому повторные вызовы для того же модуля не повторяют попытку. Неизвестную версию повторять бесконечно не нужно; достаточно однократного сообщения со статусом и причиной, чтобы неполная поддержка не выглядела штатной работой.

5. **P2 — владение привязано к координате, а не к экземпляру.** owners и ассоциативная переменная читаются по packedCoords. API не очищает их при удалении объекта. Если на том же входе появляется другой зарегистрированный объект, он может получить прежнего владельца. Для узкого сценария option 879 это не обязательно проявится; для общего API нужен явный жизненный цикл: сброс при удалении/замене либо документированная обязанность вызывающего кода нейтрализовать объект до удаления.

6. **P2 — отсутствует актуальная оценка стоимости подсветки.** Маски строятся двумя нативными отрисовками на кадр и живут до сброса карты; на прогретом пути остаются обходы слоёв, тайлов и пикселей. Это не доказательство тормозов. Нужны сравнение включено/выключено, первый проход/прогретый кэш и память на насыщенной анимированными DEF карте в 16/32 битах. Размер поверхности и анимационные кадры здесь важнее числа экспортов API.

7. **P2 — релиз пока нельзя воспроизвести только из отслеживаемых исходников.** В текущем git status ObjectGlow.cpp/.h, ObjectGlowParticles.h и TextServices.cpp не отслеживаются, хотя проект их компилирует/подключает. Это рабочий каталог, не готовый состав релиза. Перед фиксацией проверить полный production-список; временные тесты и их результаты не включать в staging.

8. **Поддерживаемость.** У собственного плагина нет обработчика OnReportVersion и явной версии продукта, как у соседнего ERA_JsonOverrides. Версии отдельных ABI не заменяют версию сборки. README начинается с узкого исторического сценария и содержит отчёты о локальных установках; перед публикацией вынести историю из основной инструкции, добавить краткие требования/зависимости, список включённых возможностей и ограничения. Не называть содержимое CONFIG_SERVICES.md полной централизацией всех конфигурационных владельцев.

## Что проверено заново

- Release|Win32 успешно собран с локальным v141_xp, /MT. MapToDbgmap отдельно собран с v143. DLL, PDB, MAP и DBGMAP созданы в `%TEMP%/ErmFunctionsReleaseReview-20261024/`; установленная игра не заменялась.
- PE: x86, 15 недекорированных экспортов совпадают с .def, соглашения stdcall подтверждаются символами линкера. В таблице статических импортов только KERNEL32.dll; это не означает отсутствия динамических зависимостей от ERA/patcher/игры.
- Размер проверенного .era: 295424 байта. SHA-256: `B083D271B11C305F1E9FD9D3767CB8263CE834663128956918CD2739D4D03910`.
- Прошли 13 автономных исполняемых проверок: RuntimeState, JsonConfig, ObjectGeometry, ObjectReplacementAllocation, GraphicsPixels, GraphicsAbi, ConfigServices, ConfigTyped, ConfigClients, TextServices, ConfigModel, ObjectReplacementHooks и HdMinimapLayout. Последние две используют настоящий patcher_x86.dll и установленный HD_WOG.dll соответственно. Проверка сигнатур HD не является проверкой изображения в игре.
- Штатный RunConfigTests.cmd и обычная сборка первоначально остановились из-за отказа записи в существующие build/obj-файлы. Проверки пересобраны в отдельном временном каталоге; MapToDbgmap также изолирован, после чего основной проект собран без повторного построения ссылки. Полный RunConfigTests.cmd с вложенными наборами других проектов не завершался и не объявляется пройденным.
- Исторические игровые прогоны, описанные в CONFIG_SERVICES.md/GRAPHICS.md, заново не выполнялись. Игра и редактор в рамках этого аудита не запускались.

## Критерии выпуска

1. Зафиксировать production-состав и версию сборки; собрать согласованный комплект сервисного плагина и изменённых клиентов/скриптов. Зафиксировать минимальную проверенную ERA и HD; ERA 3.9.29 требуется именно синтаксису SN:F Plugin:Export, а не автоматически любому способу вызова API.
2. Разрешить P1 по замене и сетевому поведению комплекта. Параллельно исправить проверку готовности хуков и добавить диагностику отказов.
3. Прогнать текущий бинарник: новая карта, загрузка старого/нового сохранения, выход и другая карта на тех же координатах, захват двумя игроками, объект под героем, туман, два replay подряд, подсветка в 16/32 битах, замены банков/жилищ/сундуков и края карты. Проверить сеть отдельно, включая передачу хода и соответствие наград/владения на обоих клиентах.
4. Проверить экспорт и перезагрузку языка вместе с текущими версиями всех потребителей, включая восстановление исходного текста после удаления JSON-ключа и редакторский комплект.
5. После этих проверок выпускать стабильную версию. До них корректная маркировка — release candidate с перечисленными ограничениями, без обещания полной сетевой поддержки и измеренного ускорения всей игры.
